# Agent Note: 运行期端点目录

Status: implemented

[English](2026-09-17-runtime-endpoint-catalogs.md) | 中文

## 问题

pi-ai 未提供任何模型的提供方——AMAX Token Router 网关、按账号或自托管的端点——必须在配置中逐个列出模型，请求才能解析到模型。配置界面早就能读取这类端点的 `GET /models` 列表，但该读取只产出供人保存的元数据：`resolveRouteModels` 会拒绝既无已安装目录、又无 `models` 列表的路由，因此模型只存在于端点的路由根本无法服务请求。失败表现为一个配置错误，它给出的补救建议（「列出模型」）对模型无法事先枚举的网关而言是错的。

## 决策

既未配置 `models` 列表、已安装目录也为空、且端点协议可读（`openai-completions`、`openai-responses`、`anthropic-messages`）的路由，按端点服务路由解析。`resolveProfiles` 把该读取记录在 profile 上（`endpointCatalog`），即使面对 settings 写入也以 deferred 校验解析这类路由，并在请求路径执行读取前保持其目录为空。路由与目录卡片都未点名协议时协议默认为 `openai-completions`，端点默认为目录卡片的 `baseUrl`——这两个假设配置界面的获取动作此前已经采用。

`PiAiAdapter` 按代（其按配置缓存的单位，以 profile 映射的身份为键）只读取一次，且只读取操作点名的路由，因此无关的不可达网关不会拖慢请求。该读取复用路由自身的解析事实，并原样经 `resolveRouteModels` 物化，这使端点服务的模型与配置的模型解析结果完全一致，包括路由声明的默认值与网关的兼容性怪癖。读取失败按路由保留，由该路由上的请求以端点自身的带 code 故障（无法访问的 URL、被拒绝的凭据、超时）上报；`listModels` 返回空而非抛错，因为不可读的目录提供不了任何模型。配置了路由 `timeoutMs` 时，读取受其限制。

## 备选方案

**在配置时把发现的列表写入 `settings.yaml`。** 这让端点的应答持久且可见，但会让 harness 拥有一份会静默过期的副本，需要由只读的检查动作触发 settings 写入，并与「`settings.yaml` 是决定路由服务内容的唯一事实」相矛盾。

**在每次操作前读取所有端点服务路由。** 比按代缓存简单，但会在每个请求前安排一次网络往返，并让一个坏掉的网关拖慢其他所有路由的请求。

**按进程而非按配置缓存读取结果。** 更省资源，但部署在修改路由端点或密钥后会继续服务旧端点的模型直到重启；以配置为键可让读取与其来源配置同样新鲜。

**以空目录解析端点服务路由并报 `UNKNOWN_MODEL`。** 这丢掉了真正解释失败原因的诊断，使运维人员去修模型 id 而不是端点。

## 后果

请求路径现在可能在首次模型调用前执行网络 I/O，仅发生在首次需要该端点服务路由的操作上；同一配置下的后续操作复用该读取。端点新增提供的模型要到配置变更或进程重启后才可见，而列出了单个坏模型的路由会因配置已枚举目录而整条不可读。`llm-pi-ai` 包测试覆盖了资格判定、读取的物化、按代复用、配置变更后重读、两种失败形态、路由超时上限，以及针对本地端点的完整「列表＋补全」请求。
