# Agent Note: 用滑块选择会话内容宽度

Status: implemented

[English](2026-09-17-conversation-width-slider.md) | 中文

## 问题

会话记录宽度只能通过拖动内容列两侧两条 40px 的 col-resize 长条来调整。该控件没有键盘或辅助技术路径，为让自身命中区域可放置而占用每侧 88px 的列预算，必须靠跟随指针的辉光才被发现，且其手势模型（对称向外位移、只有真正移动才算提交）对用户不可见。它写入的值本就是一个有界数字，而这正是滑块存在的意义。

## 决策

`ui-primitives` 新增 `Slider`：基于原生 range input 的受控数值输入，`label` 必填、可选的本地化 `valueText`、步长一像素。会话把它渲染为会话体内滚动区上方的一条长条，因为处于文档流中的长条不会遮挡它所调整的记录。其范围为 `[640, columnWidth - 176]`，位置即解析后的宽度，因此控件自身长度就展示了它设定的宽度，且只在有记录时（active 阶段）出现。每一步都会发布 CSS 覆盖并存储解析后的宽度，从而淘汰了拖拽所需的「只有真正移动才提交」规则：range input 不存在按下但未改变的状态。两条长条、其辉光与指针捕获管线一并删除；存储偏好的键与解析钳制不变，因此用户已经选定的宽度保持原尺寸。

## 备选方案

**保留长条并在旁边加键盘路径。** 一个值配两套交互模型，而长条依然占用它当初为之设计的列预算。

**把滑块塞进按钮背后的浮层。** 控件的效果随之消失，这与宽度控件需要的正好相反。

**引入外部滑块依赖。** 该控件只是一个被样式化的原生输入；依赖会为四十行标记带来组件树、主题面与升级路径。

## 后果

会话处于活动状态时，长条占据记录上方约 24px 的垂直空间，并且在选出 composer overlay 的视图中保持隐藏——与原先的长条完全一致。列较窄时选定的宽度按该列钳制后存储，这与原先被钳制的拖拽提交方式相同。该原子组件自带测试，会话侧测试覆盖往返、下限、列收缩后的重钳制，以及不渲染该控件的 hero 状态。
