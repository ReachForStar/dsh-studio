# Agent Note：在文档预览里编辑工作区文件

Status: implemented

[English](2026-09-17-workspace-file-editing.md) | 中文

## 问题

文档预览通过 `workspaceFiles` 读取文件，却无法写回：该服务只暴露 `read`、`readBytes`、`readAll`、`readRelated`、`stat`、`list`、`changes`，模块注释也明说「本服务不暴露任何变更操作」。于是改一个文件就得离开面板去用终端或模型工具，哪怕面板本来就持有文件内容和它的版本号。

## 决策

`workspaceFiles` 新增 `write(scope, path, text, guard, signal)`，`ui-sidebar-documentpreview` 的文本类查看器在其上提供编辑器。

写入复用服务既有的检查，并新增两条。`locateWritable` 是 `locateFile` 加包含性判断：读取可以落在工作区之外的路径上（预览一个并不属于本工作区的文件仍是预览），写入则必须留在工作区内。编辑器读到的版本作为 `expectedVersion` 传出，落到文件系统 seam 的 `replaceIfVersion` 意图上，因此底下被改动过的文件以 `workspace-file/stale-version` 失败而不是被覆盖；后端的 `FS_STALE_VERSION` 与既有的「非文本拒绝」一样按错误码识别，因为错误类属于提供方实际加载的那个 `dsh-fs` 实例。新内容同样受 `maxFileBytes` 上限约束，`fs.writeText` 原子替换文件。

客户端把编辑器放在 pane 上而不是各个 body 渲染器里，于是一个控件覆盖纯文本、代码与 Markdown。打开编辑器会先把剩余页读完：取自已加载前缀的草稿会把文件截断，而保存是整文件替换。保存携带 `current.version`；提交后把该 tab 持有与观测到的版本一起推进到回报的版本，这样面板的变更提示条不会把读者自己这次写入报成外部变更。face 沿用与读取相同的结算规则：tab 已结束、或读取代际已前移的写入不落任何状态。

## 备选方案

**把编辑器放进每个文本渲染器。** 一条保存路径变成三份实现，版本守卫要在三处保持正确，而且 Markdown 还得单独回答同一个文件的问题。

**只在整文件能一次读完时才允许保存。** 面板正是按页读取，因为文件可能超过一页上限；因为传输层而拒绝编辑大文件，是凭空造出的产品限制。

**不假思索地信任读取结果并直接写。** 没有 `expectedVersion`，一次保存会静默丢弃读取之后发生的模型编辑、工具写入或另一个窗口的保存——恰恰是这个面板无法重建的那种失败。

**用同一个端点写字节。** 文本不需要，而且文件系统 seam 没有二进制写入：docx/pptx（压缩的 OOXML）编辑必须补上它，因此记为待办，而不是用 base64 塞进一次文本调用里蒙混过去。

## 后果

会话工作区内的文本文件可以在它被读取的地方被编辑，拒绝时给出可解释的原因而不是静默覆盖。字节模式查看器（PDF、HTML、图片）与二进制格式保持只读；编辑器是纯文本，因此没有语法感知编辑，端点也不提供新建、重命名或删除。fork 客户端编辑路径的覆盖率来自 pane 自己的用例（草稿初始化、未读完先读、拒绝、快捷键、重复保存守卫）与 face 的写入用例。
